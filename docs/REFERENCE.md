# Reference

Configuration, CLI, MCP tools and HTTP endpoints of voice-coding-mcp. Setup is in the [README](../README.md) and [DEPLOY.md](DEPLOY.md); the behavior contract, with the reasons behind it, is in [DESIGN.md](DESIGN.md).

## Configuration

JSON file, path from `--config` or `VCM_CONFIG`, default `/etc/voice-coding-mcp/config.json` (the VPS layout; `deploy/mac/vcm-mac` defaults to `~/.config/voice-coding-mcp/config.json`, `deploy/linux/sb-linux` to `/home/switchboard/.config/voice-coding-mcp/config.json` for the dedicated hub user). See [config.example.json](../config.example.json), and [deploy/linux/config.switchboard.example.json](../deploy/linux/config.switchboard.example.json) for a Linux or WSL hub as the dedicated `switchboard` user. The defaults below are the VPS paths; in Mac mode put `stateDir` and `projectRoots` under your home directory.

| Key | Default | Meaning |
|---|---|---|
| `publicUrl` | (required) | Public `https` origin of the server, without a path, query or fragment (for example `https://vcm.example.com`). The MCP endpoint is `publicUrl + /mcp`, the OAuth issuer is `publicUrl`. A non-ASCII host is rejected, use punycode. In Mac mode `vcm-mac on` sets it |
| `listen.host`, `listen.port` | `127.0.0.1`, `8787` | Listen address; must be loopback unless `listen.allowNonLoopback` is set, since the server sits behind a TLS proxy on the same machine |
| `listen.allowNonLoopback` | `false` | Allow a non-loopback `listen.host`. Then anyone who reaches that address talks to the server in plain HTTP, bypassing the proxy (and on the VPS Caddy's IP restriction); leave it off unless you put your own TLS proxy on another host |
| `stateDir` | `/var/lib/voice-coding-mcp` | State: OAuth hashes, tasks, sessions, pairing window |
| `projectRoots` | `["/home/vcm/projects"]` | Directories whose subdirectories are projects. Not `/`, not the home directory or its ancestors, not containing `stateDir` |
| `claude.bin` | `claude` | Claude Code executable |
| `claude.model`, `claude.maxTurns` | `null` | Passed as `--model`, `--max-turns` when set |
| `claude.effort` | `null` | Passed as `--effort` when set: one of `low`, `medium`, `high`, `xhigh`, `max` |
| `claude.permissionMode` | `auto` | One of `auto`, `acceptEdits`, `dontAsk`, `plan`, `manual`. Never `bypassPermissions` |
| `claude.access` | `isolated` | What task runs (`run_task`, `run_tasks_parallel`, `resume_task_in_remote_control`) can reach. `isolated`: only `claude.mcpServers` (strict MCP config), no claude.ai connectors, `claude.settingSources`. `desktop`: like Claude Code on your desktop, with all your claude.ai connectors, user, plugin and approved `.mcp.json` MCP servers, minus the voice server itself (denied by `publicUrl`); setting sources `user,project,local` in folders you trusted in Claude Code, else `user` only, and `claude.settingSources` is not used. `ask_session_readonly` and `send_message_to_session` runs stay isolated in both modes. See [DESIGN.md](DESIGN.md#task-access) |
| `claude.settingSources` | `["user"]` | Settings Claude Code loads (isolated task runs, and ask and relay runs in both modes). Adding `project` or `local` trusts `.claude/settings.json` or `.claude/settings.local.json` of every project, and a repository can commit either |
| `claude.configDir` | `null` | `CLAUDE_CONFIG_DIR` for tasks |
| `claude.mcpServers` | `{}` | MCP servers available to tasks (written to the strict MCP config; with `claude.access` `desktop` added on top of your own servers, not strict) |
| `claude.extraArgs` | `[]` | Extra arguments for task runs. Rejected, also in `--flag=value` form: `--dangerously-skip-permissions`, `--allow-dangerously-skip-permissions`, `--permission-mode`, `--permission-prompts`, `--mcp-config`, `--strict-mcp-config`, `--setting-sources`, `--settings`, `--allowedTools`, `--allowed-tools`, `--tools`, `--add-dir`, `--system-prompt`, `--append-system-prompt`, `--bare`, `--name`, `-n` |
| `claude.env` | `{}` | Extra environment variables for tasks |
| `tasks.syncWaitSeconds` | `25` | How long `run_task` waits before returning a task number |
| `tasks.timeoutMinutes` | `15` | Hard limit per task |
| `tasks.maxConcurrent` | `2` | Parallel runs. At most one `run_task` run per project and one ask or message run per session at a time |
| `tasks.maxQueued` | `10` | Queue length |
| `tasks.resumeWithinHours` | `12` | Resume the project's last session if it was active within this time |
| `tasks.keepDays` | `14` | Task files older than this are deleted (at startup and periodically) |
| `sessions.days` | `7` | `list_sessions` shows sessions active within this many days |
| `sessions.replyWaitMinutes` | `10` | How long `send_message_to_session` waits for the session's reply |
| `remoteControl.maxSessions` | `3` | At most this many Remote Control sessions opened by the server at once, counting both tasks reopened with `resume_task_in_remote_control` and tasks started with `run_task` `remote_control`. Only sessions connected to the app (or still connecting) count; a background session that lost Remote Control while its process lives does not. The error names the open sessions with their task numbers, to close one with `cancel_task`. When full, `run_task` with `remote_control` runs the task headless and says so; `0` turns `resume_task_in_remote_control` off and makes `remote_control` always run headless |
| `remoteControl.handoffToDesktop` | `false` | macOS only (ignored elsewhere, with a startup warning). After a voice session was stopped by `cancel_task` or the idle close, and once it is gone from the live registry, the server runs `open claude://resume?session=<id>` so the Claude desktop app adopts it into its own session list (the app otherwise drops stopped CLI sessions from the list). At shutdown a pending handoff gets up to 5 s before it is cancelled. The adopted session keeps its name, and the task records the handoff (`handedOverAt`, `desktopSessionId`), so `get_task_result` and `list_tasks` say the session is in the desktop app. Failures are only logged |
| `remoteControl.idleCloseMinutes` | `0` | Opt-in, meant to pair with `remoteControl.handoffToDesktop` (which keeps each closed session in the desktop app's list). Stops the server's own Remote Control sessions (session tasks and reopened tasks) that have been idle this long (registry status idle, so not waiting for an approval or an answer; timed from `statusUpdatedAt`), or disconnected from the app this long. A session task stopped this way reads as done. Checked every minute, and checked again just before the stop; `0` (the default) turns it off |
| `oauth.accessTokenHours` | `24` | Access token lifetime |
| `oauth.refreshTokenDays` | `90` | Refresh token lifetime (rotated on use) |
| `oauth.pairingMinutes` | `10` | Pairing window length |
| `oauth.redirectUris` | Claude's callbacks | Allowed redirect URIs (`https://claude.ai/api/mcp/auth_callback`, `https://claude.com/api/mcp/auth_callback`). Must be `https`; plain `http` only for the loopback hosts `127.0.0.1`, `localhost` and `[::1]` |
| `oauth.cimdClientIds` | Claude's published identity | Client ID Metadata Document URLs that may be fetched (see [CIMD](#terms)) |
| `oauth.allowLoopbackRedirects` | `false` | Allow `http` redirects to `127.0.0.1`, `localhost` or `[::1]` on any port, for testing with MCP Inspector. The server logs a warning when it is on |
| `notify.url`, `notify.headers` | `null`, `{}` | POST a short text with the task number and project name here when a background task finishes (works with ntfy); also where the watcher (`watch`) pushes. On a public ntfy server anyone who knows the topic reads the pushes: use a long random topic or an access token in `headers` |
| `notify.includeResult` | `false` | Include the result text in the notification. Never for remote jobs (`remote_status` summaries that ran in the background): their result is screen text, so their push names only the job ("Task 12 (status of fpga on dev) finished.") |
| `logPrompts` | `false` | Log prompts and Claude's stderr. When off, prompts are not logged and Claude's stderr is logged only as its length. Also the text and target of `remote_send` (otherwise machine, pane id, length and confirmation number only) and the redacted text in `stateDir/audit.jsonl` (otherwise only a keyed hash) |
| `remote.machines` | `[]` | Machines whose tmux sessions the remote tools reach (Switchboard, see [SWITCHBOARD.md](SWITCHBOARD.md#config)), at most 32. Each entry: `name` (spoken name, `^[a-z][a-z0-9-]{0,31}$`, unique, not `local`), `transport` (`ssh`, default; `local`: the bundled dispatcher as the server's own user, at most one such machine, not with `listen.allowNonLoopback`; or `agent`: the machine connects out to the hub, see `remote.agents` and [SWITCHBOARD.md](SWITCHBOARD.md#outbound-agents-machines-connect-to-the-hub); an `agent` machine has only `name`, `transport`, `sessions` and the five opt-ins below, Linux hubs only), for `ssh` machines `host` (DNS name or IP literal, no `user@`, port or brackets), `user`, `port` (`22`), `identityFile` (absolute, plain characters `A-Za-z0-9._/-`), `knownHostsFile` (default `<stateDir>/known_hosts`, same charset), `dispatcher` (`forced` for an `authorized_keys` forced command, or the absolute path of `switchboard-remote` there, which gives no protection against a compromised server), `sessions` (1 to 64 tmux session names or `fnmatch` globs of `A-Za-z0-9_.*?-`, case-sensitive; sessions that match none are invisible), `claudeHome` (`local` machines only), `allowUsage` (`true`), `allowSend` (`false`: `remote_send`, `remote_send_keys`, `remote_resize` and `remote_clear_input` on this machine; the dispatcher also needs `--allow-send`), `allowPermissionAnswers` (`false`, needs `allowSend`: a choice digit, or keys, may answer Claude Code's permission dialog; the dispatcher also needs `--allow-permission-answers`) `sendToAnyPane` (`false`, needs `allowSend`: sends and key presses to panes without Claude Code, single line and always risky; the dispatcher also needs `--send-to-any-pane`) and `allowAttachments` (`false`: `remote_attachments` and `remote_attachment`, images, audio and video from the machine's outbox; the dispatcher also needs `--allow-attachments`; see [SWITCHBOARD.md](SWITCHBOARD.md#attachments)). Startup warnings: a lone `*`, a `local` machine, an explicit dispatcher path, `sendToAnyPane`, `allowPermissionAnswers`, and an identity file that is missing, not a regular file, not the server user's, readable by others or in another user's home |
| `remote.releaseSignersFile` | `/etc/voice-coding-mcp/release_signers` | The hub's pinned allowed-signers file for release bundles (Switchboard self-update, [SWITCHBOARD.md](SWITCHBOARD.md#self-update)): a line `switchboard-release namespaces="switchboard-release" ssh-ed25519 AAAA...` (add `,git` for `deploy/hub-update`). The file and its directory must be owned by root and not writable by group or others. `release publish` and `remote_update` verify every bundle against it; without it nothing is published |
| `remote.agents.socketPath` | `/run/switchboard-relay/hub.sock` | Agent machines: where the hub listens for the relay (`agent-relay`). Absolute, at most 100 characters of `A-Za-z0-9._/-`. Its directory must be owned by the server's user, have the relay user's group and mode 2750 (`deploy/relay/tmpfiles-switchboard-relay.conf`); otherwise the hub does not listen, every agent machine is "not connected", and `status` says why |
| `remote.agents.relayUser` | `sbrelay` | The relay account; only its uid may connect to the socket (`SO_PEERCRED`) |
| `remote.agents.heartbeatSeconds` | `20` | Ping interval per agent connection, 5 to 60; no frame within 10 s after a ping closes the connection |
| `remote.agents.commandTimeoutSeconds` | `10` | Wall clock per dispatcher call on agent machines, 1 to 60 (usage calls: 120 s, background only) |
| `remote.agents.authorizedKeysFile` | `/etc/ssh/switchboard-relay/authorized_keys` | Read only by `remote-check`, which lints it (every line `restrict` plus the relay `command=` for a configured agent machine, no key twice). A startup warning when `remote.agents` is set without an agent machine |
| `remote.ssh.bin` | `ssh` | OpenSSH client |
| `remote.ssh.connectTimeoutSeconds` | `5` | `ConnectTimeout`, 1 to 30 |
| `remote.ssh.commandTimeoutSeconds` | `10` | Wall clock per dispatcher call, 1 to 60 (each tool call also stops at `tasks.syncWaitSeconds - 3`) |
| `remote.captureLines` | `60` | Screen lines of scrollback `remote_status` reads, 10 to 500 (tmux adds the visible rows; a pane on the alternate screen has no scrollback) |
| `remote.summary.enabled` | `true` | Summarise a screen with a `claude -p` run; `false` uses the heuristic (a menu's question and options, else the last meaningful screen line) only |
| `remote.summary.model` | `haiku` | `--model` of the summariser, `^[A-Za-z0-9._-]{1,64}$`. `claude.model`, `claude.effort` and `claude.extraArgs` never apply to it |
| `remote.summary.timeoutSeconds` | `15` | Hard limit for one summariser run, 5 to 120 |
| `remote.send.confirmSeconds` | `120` | Lifetime of a message `remote_send` prepared (also keys from `remote_send_keys`, sizes from `remote_resize` and clears from `remote_clear_input`), 30 to 600 |
| `remote.send.maxChars` | `2000` | Longest message, 1 to 2000 characters (after NFC normalisation) |
| `remote.send.maxPending` | `1` | Prepared messages (keys and sizes count too) kept at once per connected client (OAuth grant), 1 to 5; a new one drops that client's oldest and the read-back says so, another client's are kept |
| `remote.send.minConfirmSeconds` | `4` | `remote_send_confirm` sooner than this after `remote_send` (or `remote_send_keys`, `remote_resize`, `remote_clear_input`) is refused and the message kept, 0 to 30 (catches a model that chains both calls in one turn) |
| `remote.send.slashCommands` | `[]` | Claude Code slash commands a message may start with (names without `/`, `^[a-z][a-z0-9:-]{0,31}$`); the dispatcher's `--slash-commands` must list them too. Any other leading `/` is refused |
| `remote.send.riskyPatterns` | `[]` | Extra case-insensitive regexes (at most 64, each 1 to 200 characters) added to the built-in English risky list (push, force, delete, deploy, drop, reset or revert, merge or rebase, spending money, sudo or chmod, kill or reboot, sending mail or posting). Risky messages need the owner's explicit yes to the risky part (`risky_ok`) |
| `remote.send.knownTerms` | `[]` | Words of your projects (at most 200, each 3 to 64 letters, digits and single spaces or `_.'-` inside, such as `GreenArrays` or `my-project`) that never count as words that came from a screen. Machine names and session names without `*` or `?` count as known terms too when they are at least 5 characters long. Words you said yourself (words of 5 or more letters) in a sent message before any screen showed them do not count either, for 24 hours; not for messages sent in the first hour after the hub starts |
| `remote.send.clientApproval` | `false` | Marks `remote_send_confirm` `destructiveHint: true`, so the Claude app asks for an on-screen approval of every confirm. Breaks hands-free sending |
| `watch.intervalSeconds` | `0` | Notification watcher (Switchboard, see [SWITCHBOARD.md](SWITCHBOARD.md#notification-watcher)): `0` is off, else how often it runs the `pending_input` check, 30 to 3600. Needs `notify.url`. It pushes "fpga on dev needs a decision." (permission) or "fpga on dev asks you something." (question) once per new wait (a wait seen only on the screen after 2 checks in a row), again only after the wait was gone for a check; announced waits are kept in `stateDir/watch.json` so a restart does not repeat them. Pushes name the machine and the tmux session (or the project folder of a local session), never a Claude Code session name and never pane text |
| `watch.longTurnMinutes` | `10` | Push "fpga on dev finished its turn after 25 minutes." when a session that was working at least this long becomes idle or waiting (no second push when the same change already pushed a wait, also when that wait is confirmed one check later); `0` turns these pushes off. 0 to 1440 |
| `watch.notifyUnreachable` | `false` | Push "Machine buildbox cannot be reached." after 3 failed checks in a row, and "Machine buildbox answers again." when it answers (for an agent machine "Machine laptop is not connected." and "Machine laptop is connected again.") |
| `watch.includeQuestion` | `false` | Append the redacted question to a wait push (quoted, at most 120 characters). Separate from `notify.includeResult`: the question is screen or registry text and the push goes to a third party |
| `usage.idleGapMinutes` | `15` | Usage accounting (Switchboard, see [SWITCHBOARD.md](SWITCHBOARD.md#usage-computation)): Claude Code activity events (prompts and assistant lines) at most this far apart count as one active stretch; longer gaps are not counted. | `usage.hourlyRate` | `40` | Billable amount per active hour, 0 to 100000 |
| `usage.currency` | `EUR` | Currency of `hourlyRate`, three capital letters, spoken as is |
| `usage.overlap` | `union` | `union`: parallel sessions of one project count once; `sum`: every session counts on its own. Different projects always bill separately |
| `usage.maxTranscriptMegabytes` | `512` | Transcripts larger than this are not read and are reported as skipped, 1 to 2048 |
| `usage.prices` | `{}` | API prices in USD per million tokens by model prefix, for example `{"claude-opus-4-1": {"input": 15, "output": 75}}` (`cacheWrite5m`, `cacheWrite1h` and `cacheRead` default to 1.25x, 2x and 0.1x of `input`); the longest matching prefix wins, then the built-in table of Anthropic's published prices (the date is in `src/voice_coding_mcp/usage/prices.py`). ## CLI

```
uv run voice-coding-mcp <command> [options]
```

On the VPS use the wrapper, which runs as the service user and adds `--config /etc/voice-coding-mcp/config.json`: `sudo voice-coding-mcp <command>`. On the Mac pass `--config` yourself (`vcm-mac on` prints the exact `pair` command). On a Linux or WSL hub with the dedicated user run it as that user: `sudo -H -u switchboard /home/switchboard/switchboard/.venv/bin/voice-coding-mcp <command> --config /home/switchboard/.config/voice-coding-mcp/config.json` (`sb-linux on` prints the `pair` command). `--config` may come before or after the command; the other options belong after their command. `voice-coding-mcp -h` and `voice-coding-mcp <command> -h` show the help.

| Command | What it does |
|---|---|
| `serve` | Run the server (started by systemd on a VPS or by `vcm-mac` on a Mac). Without `CLAUDE_CODE_OAUTH_TOKEN` it logs (info) that tasks use the logged-in user's credentials, which is expected on a Mac. Stops gracefully on SIGTERM or SIGINT: no new connections, queued and running tasks end as failed ("server stopped (SIGTERM)"), at most 20 s. `--pid-file PATH` (see below) |
| `pair [--minutes N]` | Open the pairing window and print a one-time code, its expiry in local time and the connector URL. Default `oauth.pairingMinutes` (10), at most 1440. An IP is locked out for the rest of the window after 5 wrong codes; after 50 wrong codes in total the window closes. A new `pair` replaces the old code |
| `unpair` | Close the pairing window |
| `status` | Show the connector URL, the pairing window, connected clients (no secrets; client names with control characters removed; last use as "just now", "5 minutes ago", "3 hours ago", "2 days ago" or "never") and task counts by status. With agent machines also, from the running hub's control socket (`stateDir/agents-control.sock`), each one connected or not: since when, dispatcher version, send and usage opt-ins, the address it connected from, replacements in the last hour, policy disagreements; or that the hub is not running |
| `revoke-all --yes` | Remove every client and token; the connector has to be paired again. Refuses without `--yes` |
| `remote-check [machine]` | Call `version` and `list` on every machine of `remote.machines` (or one) and print what the dispatcher reports: its version, verbs and opt-ins, the allowed sessions with Claude Code's state, the machine's config warnings, and a warning when the server user's Claude Code `settings.json` defines hooks (the summariser loads user settings, so in same-user and `local` mode the owner's own hooks and enabled plugins run for every summary). Agent machines are checked by the running hub over their live connection (through its control socket; "not checked" when the hub is not running), and the relay key file (`remote.agents.authorizedKeysFile`) is linted when readable. Exit 1 when a machine failed, 2 for an unknown machine |
| `remote-dispatcher` | Print the `switchboard-remote` dispatcher script (needs no config), for example `voice-coding-mcp remote-dispatcher > ~/.local/bin/switchboard-remote` on the machine to reach |
| `remote-connector` | Print the `switchboard-connect` script (needs no config), for a machine that connects out to the hub |
| `remote-hook` | Print the `switchboard-hook` script (needs no config): the Claude Code hooks and the `notify_owner` MCP server of a machine, see [SETUP-AGENTS.md](SETUP-AGENTS.md#session-hooks-and-notify_owner) |
| `agent-relay --machine NAME [--socket PATH]` | The relay between one machine's SSH connection and the hub's socket (needs no config). The relay account's `authorized_keys` runs it as `<venv>/bin/python -I -m voice_coding_mcp.remote.relay --machine NAME` (the same entry point, with `-I`); this command form is for manual tests. Exit 1 when the hub is not running or its socket fails the checks, 2 for bad arguments, 3 for a frame over 5 MiB from the machine |

Exit codes: 0 success, 1 runtime error, 2 usage or config error. A usage error prints the usage line and the reason to stderr.

`serve --pid-file PATH` writes the server's pid to `PATH` (mode 600; a missing parent directory is created with mode 700) and holds an exclusive `flock` on the file for the server's whole lifetime. On a clean exit (including a graceful SIGTERM or SIGINT) the file is removed. When another process holds the lock, `serve` prints `Error: another server holds the pid file PATH (pid N)` and exits with 1 without starting. A file left behind by a crash or `kill -9` is stale exactly when its lock is free, and the next `serve` takes it over. `vcm-mac` starts the server with `--pid-file <run dir>/server.pid` and decides from this lock whether its server is running.

`serve` logs JSON lines to stdout (journald on the VPS, `vcm-mac-server.log` on the Mac): one line per request with method, path without query, status, duration, client IP and a token fingerprint, never headers or bodies. Prompts and Claude's stderr appear only with `logPrompts`.

The CLI and the running server share `stateDir`: changes to `oauth.json` and `pairing.json` are serialized across processes with file locks (`oauth.lock`, `pairing.lock`), and the server notices changes made by the CLI.

## deploy/linux/sb-linux

On and off for a Linux or WSL hub published through Tailscale Funnel (Switchboard; steps in [SETUP-WSL.md](SETUP-WSL.md)). Run it as yourself, the Tailscale operator (`sudo tailscale set --operator=$USER` once), never as the hub user. Install it (and the dispatcher and the unit) only from your own clone at a verified commit, never from the hub user's checkout ([SETUP-WSL.md](SETUP-WSL.md#your-own-copy-the-only-source-for-what-runs-as-you-or-as-root)). Needs bash, jq, curl and util-linux `flock`; in service mode also sudo and systemctl, in user mode uv (unless `SB_VCM` is set).

| Command | What it does |
|---|---|
| `on` | Checks Tailscale (`tailscale status --json`: connected, MagicDNS name), runs `set-public-url https://<name>` (as the hub user in service mode), starts the hub (service: `sudo systemctl start`, or `restart` when `publicUrl` changed; user: `voice-coding-mcp serve --pid-file` in the background), waits for `/healthz` (`SB_START_SECONDS`, default 30; a service that does not answer is stopped again), then `tailscale funnel --bg <port>` and checks `tailscale funnel status`. Prints the connector URL and the pair command. If Funnel or HTTPS still need approval it prints Tailscale's link, stops the hub and exits 1 |
| `off` | `tailscale funnel --https=443 off`, only when the Funnel proxies the hub's port; then stops the hub (service: `sudo systemctl stop`; user: SIGTERM to the pid in the pid file, SIGKILL after 25 s). Safe to run twice |
| `status` | On or off, the mode, the connector URL, the service state or server pid and port, then `voice-coding-mcp status` (as the hub user in service mode) |

In service mode everything the hub user's `voice-coding-mcp` prints (stdout and stderr of `set-public-url` and `status`) is passed through `tr -d` of the control characters except tab and newline, so the hub cannot send terminal escape sequences to your terminal.

| Variable | Default | Meaning |
|---|---|---|
| `SB_MODE` | `service` | `service`: the hub runs as a dedicated user under the systemd unit `SB_SERVICE` (`deploy/linux/switchboard.service`). `user`: the hub runs as you, started in the background like `deploy/mac/vcm-mac` |
| `SB_USER` | `switchboard` | Service mode: the hub's Linux user. `on` refuses to run as this user |
| `SB_SERVICE` | `switchboard` | Service mode: the systemd unit |
| `SB_CONFIG` | service: `/home/<SB_USER>/.config/voice-coding-mcp/config.json`; user: `~/.config/voice-coding-mcp/config.json` | The hub's config file |
| `SB_VCM` | service: `/home/<SB_USER>/switchboard/.venv/bin/voice-coding-mcp`; user: `uv run --frozen` in the repository | The `voice-coding-mcp` executable |
| `SB_PORT` | `8787` | Service mode: `listen.port` of the hub's config (the file is closed to you). User mode reads `listen.host` and `listen.port` from the config |
| `SB_RUN_DIR` | `~/.local/state/sb-linux` | Your lock file (`on` and `off` are serialized with `flock`), and in user mode the server log, pid file and Funnel port file, all private |
| `SB_TAILSCALE` | `tailscale` on `PATH` | The Tailscale CLI |
| `SB_START_SECONDS` | `30` | How long `on` waits for `/healthz` |

## deploy/hub-update

The hub's own signed update (steps in [DEPLOY.md](DEPLOY.md#signed-updates-of-the-hub), design in [SWITCHBOARD.md](SWITCHBOARD.md#self-update)). The remote tools reach machines only through `switchboard-remote` (see [SWITCHBOARD.md](SWITCHBOARD.md#the-dispatcher)): over SSH with a dedicated key that the remote `authorized_keys` binds to the dispatcher with a forced command (`command="/usr/bin/python3 -I /home/USER/.local/bin/switchboard-remote --sessions 'fpga,notes'"`, plus `restrict` and `from=`), or as a local child process for a `local` machine. Text they quote from screens is untrusted. Usage needs `--allow-usage` there (and `allowUsage`, the default, in the machine's config); it reads every transcript under that user's Claude Code home and sends only project folder names, model names, ids, times and token counts. Sending needs the dispatcher's own opt-ins in that forced command too: `--allow-send`, and only if wanted `--allow-permission-answers`, `--send-to-any-pane` and `--slash-commands compact,clear`. A dispatcher older than 0.3.0 has no `send` verb or an older form of it, and refuses every send ("too old for sending"); one older than 0.5.0 has no `keys` and `resize` verbs (key presses and window sizes then say "too old"). One older than 0.11.0 has no `clear` verb (`remote_clear_input` then says "too old") and reports Claude Code's grey prompt suggestion as typed text, so a send into an input that shows one is refused as if something were typed. The same `--allow-send` (and for a permission dialog `--allow-permission-answers`, for panes without Claude Code `--send-to-any-pane`) covers keys and window sizes. Attachments need `--allow-attachments` (and `allowAttachments` in the machine's config); `--outbox /absolute/path` replaces the default outbox `~/.local/share/switchboard/outbox` (nobody creates it; it must be the dispatcher user's own directory, not writable by group or others). A dispatcher older than 0.7.0 has no attachment verbs ("too old for attachments").

Session names are the session titles (the desktop app title, or "project: first prompt" when there is none), matched like project names. The target session sees a message from another session, not your approval; a session in a different permission mode may hold it until you approve it in the desktop app, and the result then says that the message was not picked up. Sessions are read from Claude Code's internal files (`~/.claude/projects`, `~/.claude/sessions`, or under `claude.configDir`), see [DESIGN.md](DESIGN.md#the-owners-sessions). Session ids, wherever they come from, must be UUID-shaped before they are passed to `--resume`.

Name matching (projects and sessions) ignores case and accents (for example, a non-English title: "prihlaseni" finds the Czech "Přihlášení") and is loose: "alpha app" finds `alpha-app`. Queries shorter than 3 characters only match exactly. A name that contains the query (prefix or anywhere) needs a query of at least 3 characters. A name counts as contained in the query only as whole words of the query, so "website redesign" does not pick a project called `web`. Small typos are forgiven: one wrong letter for queries up to 4 characters, two above.

Answers longer than 2000 characters are shortened in the tool result; the task file keeps up to 200 000 characters. No tool is marked destructive (except `remote_send_confirm` with `remote.send.clientApproval`), so with "Always allow" Claude does not stop to ask for confirmation in voice mode.

Tasks wait in one queue in arrival order (FIFO); a task whose project or session is busy waits while later tasks for other projects run, and tasks for the same project, or for the same session, keep their order.

## HTTP endpoints

| Path | Notes |
|---|---|
| `POST /mcp` | MCP Streamable HTTP, stateless, plain JSON answers (no SSE), bearer token required (401 with `WWW-Authenticate` otherwise). Body limit 1 MB. `GET`, `HEAD` and `DELETE` answer 405 |
| `GET /.well-known/oauth-protected-resource[/mcp]` | Protected resource metadata |
| `GET /.well-known/oauth-authorization-server` | Authorization server metadata |
| `POST /register` | [DCR](#terms). Only while a pairing window is open; rate limited per IP like `/authorize`; at most 20 clients (when full, the oldest client without a live grant or a pending authorization code is evicted). `client_name` is stored with control characters removed |
| `GET`/`POST /authorize` | Only while a pairing window is open; rate limited per IP (30 per minute) |
| `POST /token`, `POST /revoke` | Always open, not rate limited (all Claude connector traffic shares Anthropic's egress IPs) |
| `GET`/`HEAD /healthz` | `{"ok":true}`, no auth and no Host check, for local monitoring |
| `GET`/`HEAD /attachments/<token>` | A large video's one-time link (`remote_attachment`, video over 16 MiB): the hub's cleaned copy from memory, for 10 minutes, with `Range` support. No bearer token: the 256-bit token in the path is the credential. Unknown or expired tokens answer 404 and those misses are rate limited per IP like `/authorize`; the log shows only the token's fingerprint |

OAuth request bodies (JSON and forms) are limited to 16 KB. Every other request must carry `Host` equal to the host of `publicUrl` (403 otherwise). A browser `Origin`, when present, must be the `publicUrl` origin, `https://claude.ai` or `https://claude.com`. Per-IP limits and the per-IP count of wrong pairing codes treat IPv6 clients by their /64 prefix.

## Dependency updates

`pyproject.toml` sets `[tool.uv] exclude-newer = "14 days"`, and Dependabot uses the same 14-day cooldown. Dependabot relocks with uv, so it cannot propose a release younger than 14 days, security fixes included ([dependabot-core#16984](https://github.com/dependabot/dependabot-core/issues/16984)). For an urgent fix, exempt that one package in `pyproject.toml`:

```toml
[tool.uv]
exclude-newer = "14 days"
exclude-newer-package = { <package> = "1 day" }   # a duration, a date such as "2026-11-20", or false
```

Then run `uv lock --upgrade-package <package>` and commit `pyproject.toml` and `uv.lock`. Remove the override once the release is older than 14 days and run `uv lock` again.

## Terms

- **Custom connector**: a remote MCP server you add to Claude yourself (Settings, Connectors). See Anthropic's [guide to custom connectors](https://support.claude.com/en/articles/11175166-getting-started-with-custom-connectors-using-remote-mcp).
- **Remote Control**: a Claude Code feature that lets you continue a session running on your machine from the Claude app or claude.ai. See the [Remote Control docs](https://code.claude.com/docs/en/remote-control).
- **DCR** (Dynamic Client Registration, [RFC 7591](https://datatracker.ietf.org/doc/html/rfc7591)): the client registers itself at `/register` and gets a client ID.
- **CIMD** (Client ID Metadata Document, [IETF draft](https://datatracker.ietf.org/doc/draft-ietf-oauth-client-id-metadata-document/)): the client ID is an `https` URL whose JSON document describes the client, so no registration is needed. This server fetches only the URLs in `oauth.cimdClientIds`.
